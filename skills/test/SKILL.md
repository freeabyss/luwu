# Test Skill - 测试全流程助手

## 文件组织规范

### `iterations/vX.Y.Z/test/` 只放**文档**

用例文档和测试报告统一放到当前迭代目录下的 `test/` 子目录，与 leader 技能的迭代双轨制对齐：前 5 个状态只写迭代目录，⑥ 上线后再由归档 subagent 合并到全局 `doc/`。

```
iterations/
└── vX.Y.Z/
    └── test/
        ├── README.md               # 用例与报告索引
        ├── cases/                  # 测试用例（按功能模块分文件）
        │   ├── user-testcases.md
        │   ├── product-testcases.md
        │   └── order-testcases.md
        └── report/                 # 每次执行的完整报告
            ├── test-report-20260701-1430.md
            └── test-report-20260702-0930.md
```

**这个目录只允许出现两类文件**：`cases/*.md`（用例文档）和 `report/*.md`（测试报告）。不要往这里放 `.java` / `.ts` / `.py` 等测试脚本、构建配置或运行产物。

**为什么**：文档是"给人看的产出"，随迭代归档最合适；报告是"某次执行的快照"，按迭代聚合能形成质量档案。跨迭代混放会让"这一版交付了什么"这个问题变得模糊。

### 测试代码：按语言约定就近放，不进迭代目录

测试代码跟随源码走，遵循各语言/框架的官方约定。硬拆到 `iterations/` 会破坏 IDE 索引、测试运行器发现机制和 CI 构建流程。

速查：

| 技术栈 | 位置 |
|--------|------|
| Java (Maven/Gradle) | `src/test/java/...`（与被测类同包名） |
| Vitest / Jest | `*.test.ts` 与源码共置，或统一放 `__tests__/` |
| Playwright / Cypress | 项目根下 `tests/` 或 `e2e/` |
| pytest | 顶层 `tests/` 或包内 `tests/` |
| Go | `foo_test.go` 与被测文件同目录 |
| Rust | 单测在文件末尾 `mod tests`；集成测试放 `tests/` |

各技术栈的完整目录示例、共置 vs 集中的取舍见 `reference/code-location.md`。

### 用例文件：按功能模块拆分

在 `iterations/vX.Y.Z/test/cases/` 下，每个功能模块一个文件：

```
cases/
├── user-testcases.md          # 用户模块
├── product-testcases.md       # 商品模块
├── order-testcases.md         # 订单模块
└── payment-testcases.md       # 支付模块
```

- **模块粒度**参考 PRD 功能清单或代码的领域划分（用户、商品、订单、支付、健康档案……）
- **单文件超过约 500 行或 50 个用例时进一步细拆**：按子模块或核心场景，如 `order-create-testcases.md`、`order-refund-testcases.md`
- **命名**：`{module}[-{子模块}]-testcases.md`，小写连字符
- **索引**：`iterations/vX.Y.Z/test/README.md` 维护一张表，列出本迭代所有用例文件及其覆盖范围
- **跨迭代复用**：若某用例在新迭代仍适用，**复制过去**而不是引用旧迭代文件——保证每个迭代的用例集自包含

功能模块是 PRD 和 Domain 模型共同的组织单元，用例贴着功能走能与需求、代码天然对齐。

### 报告文件：一次执行 = 一份文件

- **目录**：`iterations/vX.Y.Z/test/report/`（不存在先 `mkdir -p`）
- **命名**：`test-report-{YYYYMMDD-HHmm}.md`，例如 `test-report-20260701-1430.md`
  - 若只测某个模块，加后缀：`test-report-20260701-1430-order.md`
- **一份文件包含本次执行全部内容**（统计、覆盖率、失败详情、结论），不要拆碎
- **不覆盖历史**：每次生成新文件，本迭代内的历史报告用于回归趋势对比
- **只写当前迭代**：历史迭代目录只读归档

一次执行 = 一份完整报告，归档、分享、diff 都方便。碎片化的报告会丢失执行上下文。

## 核心工作流

```
需求/代码 → 用例生成 → 用例评审 → 执行测试 → 结果分析
```

## 1. 用例生成

**基于需求**：读 PRD，抽功能点，按下面五个维度铺场景：

- **Happy Path**：正常主流程
- **Boundary**：极值、空值、最大最小、边界前后
- **Exception**：非法输入、外部依赖失败、并发冲突
- **Performance**：响应时间、并发量、数据量
- **Security**：越权、注入、鉴权失效

**基于代码**：识别函数的分支（if/else/switch/循环），为每条路径设计一条用例。

### 用例模板

| ID | 用例名称 | 前置条件 | 测试步骤 | 预期结果 | 优先级 | 类型 |
|----|---------|---------|---------|---------|--------|------|
| TC-001 | 正常登录成功 | 账号已注册 | 1. 输入正确账号密码 2. 点击登录 | 跳转首页 | P0 | 功能 |

### 测试类型选择

| 类型 | 用于 | 重点 |
|------|------|------|
| 单元测试 | 单函数/单组件 | 参数边界、返回值、异常 |
| 集成测试 | 模块间交互 | 数据流转、接口契约、错误传递 |
| 端到端 | 完整业务流程 | 用户路径、跨页面状态、真实环境 |
| 回归测试 | 变更后验证 | 核心功能不受影响 |

**测试金字塔原则**：单元测试量最大（快、稳），集成测试适量，E2E 最少（慢、脆）。

### 项目特定规范

**Java（DDD 项目）**：单元测试仅限领域层；API 接口测试用 REST Assured 打真实 HTTP，不用 `@SpringBootTest`，测试与服务启动解耦；每个接口一个 Test 类。详细规则和 10 条编写要点见 `reference/java-testing-rules.md`。

## 2. 用例评审

评审用例文档时对照下面清单，逐条勾：

- [ ] **覆盖完整性**：所有需求点是否都有用例？
- [ ] **边界充分性**：极值、空值、非法输入是否覆盖？
- [ ] **可执行性**：步骤清晰可重复，预期结果明确？
- [ ] **独立性**：用例之间不互相依赖？
- [ ] **优先级合理**：P0 覆盖核心路径，P1/P2 覆盖边缘？
- [ ] **负面用例**：错误输入、异常情况是否覆盖？

评审结论三选一：

- ✅ **通过**：可以直接执行
- ⚠️ **需补充**：标注缺失场景，建议补充点
- ❌ **需重写**：用例逻辑错误或预期不明确

---

## 3. 执行测试

### 执行前检查

- [ ] 测试环境就绪
- [ ] 测试数据准备完成
- [ ] 依赖服务可用
- [ ] 测试框架配置正确

### 执行流程

1. **按优先级跑**：P0 → P1 → P2，先保证核心路径
2. **记录结果**：每个用例通过 / 失败 / 阻塞；失败要抓截图、日志、堆栈
3. **收集覆盖率**：行覆盖率、分支覆盖率、函数覆盖率；核心模块目标 ≥ 80%
4. **产出报告**：按下方模板写到 `iterations/vX.Y.Z/test/report/test-report-{时间戳}.md`

---

## 4. 失败用例分析

**分析模板**（每个失败用例一段）：

```
【失败用例】TC-XXX - 用例名称
【失败现象】实际结果描述
【失败原因】根因分析
【修复建议】具体修复方案
【影响范围】影响的模块/功能
【严重程度】Blocker / Critical / Major / Minor
```

**常见失败分类**：

| 类型 | 原因 | 处理 |
|------|------|------|
| 断言失败 | 预期与实际不符 | 确认需求，改代码或改断言 |
| 环境问题 | 依赖服务不可用 | 修环境后重跑 |
| 数据问题 | 测试数据过期 | 更新测试数据 |
| 时序问题 | 异步超时 | 加等待机制或调超时时间 |

---

## 5. 测试报告模板

写到 `iterations/vX.Y.Z/test/report/test-report-{YYYYMMDD-HHmm}.md`。一次执行 = 一份文件，不要拆。

```markdown
# 测试报告 - {项目名}

- 执行时间：YYYY-MM-DD HH:MM
- 执行环境：{dev/staging，OS，JDK 版本 等}
- 执行范围：{功能模块 或 全量，例如 user+order / 全量回归}
- 执行人：{人 or CI}
- 用例来源：{对应的 cases/*.md 文件列表}

## 一、总体统计
| 指标 | 数值 |
|------|------|
| 总用例数 | N |
| 通过 | X (X%) |
| 失败 | Y (Y%) |
| 阻塞/跳过 | Z (Z%) |
| 执行时长 | HH:MM:SS |

## 二、覆盖率
- 行覆盖率：XX%
- 分支覆盖率：XX%
- 函数覆盖率：XX%

## 三、失败用例详情
（每个失败按"失败用例分析"模板逐个列）

## 四、结论与建议
- 是否通过测试：✅ / ❌
- 遗留风险：...
- 后续建议：...
```
